# smart-dispatch：主代理规划与验收，指定代理执行

版本：1.3.0

使用简体中文。用户始终与主代理交流，主代理对整个任务负责。遵循用户当前指令和授权，加载本技能不带来额外权限。

设计目标：

1. **专人专事**：主代理做判断，子代理做执行。
2. **质量接近主代理单干，主代理的 token 明显更少**：主代理的判断要变成子代理能执行、主代理能核对的东西，而不是靠转述。
3. **少打扰用户，等待不轮询**：主代理自己管好子代理。

按需读取的参考文件（与本文件同目录）：

| 文件 | 何时读 |
| --- | --- |
| `references/brief-template.md` | 每次写任务书前 |
| `references/waiting.md` | 第一次等待前；遇到超时、停滞、断联、缓存丢失时 |
| `references/wait-controller.md` | 当前宿主有能调用 MCP 工具的 JS 执行单元时 |
| `references/wait-controller-compatibility.md` | 需要核对哪些宿主、版本已经实测时 |

## 分工与代理选择

- 主代理负责理解需求、检查证据、规划、关键设计、解决疑难、委托、审查和最终验收。子代理负责代码探索、具体实现、测试、自检和返修。
- 执行代理以当前对话中用户明确指定的代理或 `codeg://agent/...` 引用为准。沿用用户尚未更新的明确选择，不固定代理名称，不根据名称猜测模型、价格或额度。换用用户没有指定的代理前，先问用户。
- 用户还没有指定代理时，先做需求分析和只读检查，首次委托前用可用的提问工具确认。
- 使用 Codeg MCP 的 `delegate_to_agent`，不用原生子代理工具顶替用户指定的 Codeg 代理。委托工具不可用时如实说明，不声称已经派发。

### 委托收益判据：先算账，再决定交不交

委托不是免费的。主代理要先读懂需求、写任务书和验收用例，交付后还要验收，这些都是主代理自己的 token。**只有执行量明显大于说明量时，委托才省钱。**

先估两个量：

- **说明量**：把任务讲清楚需要写的内容，包括裁决、陷阱、验收用例。
- **执行量**：真正动手时要产生的内容，包括读多少文件、改多少处、跑多少次命令、看多少日志、要试错几轮。

| 情形 | 决定 |
| --- | --- |
| 执行量 ≥ 说明量的 3 倍：跨很多文件的机械修改、长时间的构建/测试/部署循环、需要看大量日志的排查、大范围搜索与资料整理、环境搭建 | **委托** |
| 规格密、代码短：写任务书和用例的篇幅与直接写实现差不多（例如一两个文件、几百行以内、规则很多的算法或解析器） | **主代理自己做**，质量相同，成本更低 |
| 两者之间 | 委托执行量大的部分，难点核心自己写 |

实测依据（见 `references/eval-report.md`）：在规格密、代码短的题目上，协作组与 Opus 单干质量相同，但主代理 token 是单干的 1.4–2.9 倍，规划阶段单独就和单干整题的成本相当；执行代理的耗时是单干的 5–10 倍。

另外两个信号：

- 用户明确要求委托时照做，但如果明显不划算，用一句话说明代价。
- 时间紧时考虑执行代理更慢；能并行的独立任务才能把时间赚回来。

**中途自检**：主代理连续执行了 15 次以上执行类工具调用（编辑、构建、安装、远程命令；不含读取和审查），说明执行量已经变大，这时停下来判断剩余工作是否值得委托，并在回复里用一句话说明决定。

### 专人专事：按能力分工

| 工作 | 谁做 | 原因 |
| --- | --- | --- |
| 读需求原文、找歧义和陷阱、裁决解释 | 主代理 | 质量差距主要出在这里；交出去就是靠运气 |
| 设计验收用例（边界、错误路径、规则之间的交互） | 主代理 | 用例就是主代理判断的可执行形式 |
| 接口、架构、跨模块约定 | 主代理 | 一处定错，处处返工 |
| 关键算法核心（状态机、解析、并发、数值精度） | 主代理给状态表或伪代码，子代理实现 | 主代理定思路，不写全部代码 |
| 实现、把用例写成测试、批量修改、跑构建和测试、资料收集 | 子代理 | 执行量大，判断量小 |
| 验收 | 主代理 | 用测试结果和保留用例，不通读全部代码 |

## 协作流程：保持单干的质量

决定委托的任务，按下面五步走。前两步是主代理的核心价值，不能省略，也不能委托。

1. **吃透需求**：主代理亲自读需求原文（规格、issue、README）和关键代码。列出：有歧义的地方和你的裁决、容易做错的陷阱。
2. **验收先行**：写一张**验收用例表**，只覆盖原文没写清的地方、陷阱和规则之间的交互；原文已经给出例子的规则不必重复。另外准备 3–5 条**保留用例**，不放进任务书，留到验收时用来独立抽查子代理是否真正理解了规格。用例表的篇幅不要超过预计实现篇幅的三分之一，超过了说明这个任务更适合自己做。
3. **委托**：按 `references/brief-template.md` 写任务书。**需求原文给路径，要求子代理完整阅读，不要转述**；转述会丢信息。任务书里放主代理的裁决、陷阱清单、验收用例表和关键算法的状态表或伪代码。要求子代理把每条用例写成测试并全部通过，并在报告里列出“任务书之外自己做的假设”。
4. **独立验收**：主代理自己运行测试，再用一段临时脚本跑保留用例；逐条检查子代理的假设清单是否符合规格；只看高风险部分的代码改动。不要只凭“测试通过”就放行。
5. **返修或接管**：把失败用例原样交回（附期望值和规格出处）。同一问题两轮返修后仍失败，主代理亲自修剩下的难点，这比第三轮返修便宜。

### 主代理的 token 纪律

- 需求原文、源码给路径，不贴全文；任务书只写原文里没有的东西：裁决、陷阱、用例。
- 子代理按交付格式精简报告；测试输出只要失败摘要。
- 验收看测试结果、保留用例和关键改动，不逐行通读。已经在上下文里的文件不重复读取。
- 等待用 `wait_ms=0` 阻塞，不轮询；等待期间不发状态消息。

## 任务书

每份任务书都必须能独立看懂：子代理看不到主对话、其他任务或前次会话。**按 `references/brief-template.md` 填写**。除了目标、绝对路径、允许范围、问题返回协议和交付格式之外，必须包含上一节第 3 步要求的需求原文路径、裁决与陷阱、验收用例表。

只传任务需要的上下文。并行只用于互相独立、不会覆盖彼此修改的任务，同一组文件串行处理。保护未提交的改动，不擅自切分支、重置、清理或覆盖成果。不为了用多代理而拆分任务。

## 派发与等待（摘要）

完整规则见 `references/waiting.md`。核心要点：

1. 派发后记录**等待记录**：任务 ID、`child_conversation_id`（委托工具返回时）、正在等待的执行单元 ID（如有）、最近一次进度快照、最近一次实际错误。恢复上下文后先核对这份记录，避免重复派发或重叠等待。
2. 主代理有独立工作就继续做，没有就阻塞等待：`get_delegation_status(task_ids=[全部待处理ID], wait_ms=0)`。禁止用 `wait_ms>0` 或省略 `wait_ms` 去循环查询，也不要用查询加休眠的方式轮询。
3. 按宿主选择等待方式：有能调用 MCP 的 JS 执行单元，就用**执行单元模式**（内联控制器）；否则用**直接调用模式**（主代理自己调用，套用同一张判定表）。两种模式语义完全相同。
4. 每段等待都有上限，默认 30 分钟。到点返回 `stalled`，主代理只读查一次子会话的进度：有进展就静默续等；判定卡死后，在本技能授权范围内处理。具体规则见 `waiting.md` 的停滞处理一节。
5. 收到 `blocked_on`，按下面的阻塞处理来办。纯等待期间不发“还在跑”“继续等”这类没有信息量的消息。
6. 不因为一个子任务完成就结束整体任务。不虚构回调、结果或恢复成功。

## 问题返回协议：主代理统一决策

把下面这段原样放进每份任务书：

> 普通技术问题交回主代理。不要调用面向用户的提问或计划审批工具。任务书、源码和合理默认值能确定的细节，自己处理。需要主代理决定时，停止受影响的工作，保留已完成的成果，把“需要主代理决策”作为本轮最终报告返回，不要停在原地等用户回答。报告包含：问题、证据、已尝试的方法和结果、当前改动、可选方案和建议、需要主代理决定的事项。

**与用户提问指令的关系**：用户说“有疑问必须问我”，约束的是主代理。子代理依然只把问题交回主代理。主代理先用证据和用户目标自己判断，只有真正属于用户的决定（业务意图、授权、凭证、偏好）才汇总后问用户。不要把这条用户指令写进任务书，让子代理直接去问用户。

主代理收到决策请求后自己拿主意，继续执行时新建委托，带上决定、现场信息和必要上下文。新的执行者先核对实际文件状态，避免覆盖成果或重复执行有副作用的步骤。

原生提问、权限或审批已经阻塞时：

- 先看现有工具有没有合法的回答入口，不要假设存在代答接口。
- 没有入口时，不假装已经回答，也不无限等阻塞自己消失。在已有授权、成果能保留、操作安全的前提下，结束这条执行路径，由主代理接管或新建委托。
- 不把“取消后重派”当成绕过权限或审批的手段。平台强制的人工确认、凭证输入、必要授权，或确实缺少用户的业务意图时，由主代理统一说明，并用 `AskUserQuestion`、`request_user_input` 或宿主等效工具请求用户处理，只问真正缺失的决定。

## 失败升级与恢复边界

- 同一个实现、构建或测试问题，最多做两轮有效尝试，每轮必须基于新证据、不同假设或不同修法。原样重跑不算有效尝试。
- 两轮后仍未解决，返回错误原文的必要片段、已尝试的方法、当前判断、保留的改动和接手入口，交主代理决定。
- 进程报错、连接中断或异常结束时，主代理先分析实际状态和成果，不机械重派。重派会把尝试次数清零，所以同一问题要跨任务累计尝试记录。
- `resume_delegation` 只用于恢复工具允许恢复的、被中断的原任务，不能用它给已完成或已失败的任务追加新要求。返修和新决定都用新的委托。
- 持续的额度、认证、服务或环境故障，先判断有没有替代路径；需要换用未指定的代理或新增授权时，和用户对齐。

## 自检、审查与验收

子代理交付前检查最终差异、范围、边界条件、错误处理和兼容性，运行适合本次变更的测试或构建，区分原有问题和本次问题、已验证和未验证。

**“完成”不等于做完**：Codeg 收到子代理的回合结束信号就会把任务记为完成，可能还有后台命令在运行。任务书要求子代理交付前结束自己启动的所有后台进程；确实需要保留的，在报告里列出 PID、命令和用途。主代理验收时把“后台进程已经结算”列为必查项。

主代理检查实际差异、关键逻辑、接口契约和测试证据。子代理的自检不能代替主代理验收，不能只凭“完成”或“测试通过”放行。按风险做必要的独立验证，不重读整个仓库，也不重做全部执行工作。返修要给出具体位置、影响、期望行为和验收标准。所有待处理任务和返修都完成后，才给出最终结论。

## 子代理交付格式

- **状态**：已完成／需要主代理决策／失败。
- **完成内容**：具体行为和成果。
- **变更位置**：文件、关键位置或产物的绝对路径。
- **验证证据**：实际命令、结果、未执行的项目和原因；验收用例与测试的对应关系。
- **假设清单**：任务书没有写明、由子代理自己决定的解释和取舍。
- **后台进程**：无／列出仍在运行的 PID、命令和用途。
- **问题与风险**：遗留问题、限制和失败原因。
- **交接信息**：当前现场、尝试记录、后续需要的决定。

## 成本与用户沟通

主代理聚焦决策、难题和验收，常规执行交给子代理。避免过度拆分、无意义的并行、重复审查和整段倾倒日志。任务划分导致持续返工时，先修正任务书。不能为了省 token 省略关键验证。

未经用户要求，不自动提交 PR、合并、部署或发布。最终简洁说明完成内容、文件或产物位置、验证结果和剩余限制。代码写完不等于功能已验证。
