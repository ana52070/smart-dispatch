# 等待规则：阻塞等待、停滞处理与断联恢复

本文件是 `SKILL.md`「派发与等待」一节的完整版。判定语义只有一份，即 `scripts/wait-controller.js` 中的 `wcDecide`；本文件的判定表与它一一对应，并由测试覆盖。各宿主的实测数据只记录在 `wait-controller-compatibility.md`。

## 1. 先分清四个层次

| 层次 | 判断依据 | 应采取的动作 |
| --- | --- | --- |
| 子任务执行 | 子任务的实际状态、结果或阻塞报告 | 等待调用超时不等于任务失败，保留任务 ID |
| MCP 服务端等待 | `get_delegation_status` 的工具定义 | 使用 `wait_ms=0`（服务端无限等待） |
| MCP 客户端调用 | 实际超时报错、已生效的配置或实测数据 | 记录准确时限；服务端无限等待不代表客户端也无限 |
| 外层执行单元 | `Script running with cell ID ...` 等让出控制权的响应 | 恢复同一个执行单元，不新建等待 |

单次调用时限、累计等待时间和子任务总耗时是三个不同的量。只引用当前环境的证据，不把其他宿主或历史测试的数值当作当前时限。

## 2. 两种等待模式

| 模式 | 适用宿主 | 做法 |
| --- | --- | --- |
| **执行单元模式** | 宿主提供 JS 执行单元，单元内可以调用当前会话的 MCP 工具，并能在长时间运行后恢复同一单元（例如 Codex `functions.exec` / `functions.wait`） | 按 `wait-controller.md` 内联控制器，由控制器自动续等。外层只恢复同一个单元 |
| **直接调用模式** | 没有这样的执行单元（例如 Claude Code、CodeBuddy 等直接调用 MCP 工具的宿主） | 主代理自己调用 `get_delegation_status(task_ids, wait_ms=0)`，每次返回后套用下面的判定表 |

不确定当前宿主是否满足执行单元契约时，用直接调用模式。两种模式的判定和停滞处理完全一致，区别只是谁来执行这个循环。

## 3. 判定表（每次等待调用返回后）

| 返回情况 | 判定 | 动作 |
| --- | --- | --- |
| 合法批次中有 `completed` / `failed` / `canceled` / `unknown`，或有带 `blocked_on` 的 `running` | `actionable` | 处理这些任务，把终态任务移出集合，剩余任务继续等待 |
| 合法批次中全部是 `running` 且都没有 `blocked_on` | `protocol_anomaly` | **不轮询**，按第 6 节处理（常见原因：任务缓存丢失） |
| 整句匹配已知的标准超时诊断（Codex：`timed out awaiting tools/call after Ns`；Claude Code：`MCP server "…" tool "get_delegation_status" sent no response or progress for Ns; aborting.`），且这次调用耗时接近 N | 正常超时 | 本段等待未到上限，就用同一组 ID 续等，不发消息 |
| 同上，但调用几乎立即返回（耗时不到 N 的一半），连续 2 次 | `timeout_exhausted` | 链路异常，停止续等，只读诊断客户端配置或宿主时限 |
| 本段累计等待达到 30 分钟（或设定的调用次数上限） | `stalled` | 按第 5 节做进度检查 |
| 认证、断线、参数或其他工具错误 | `transport_error` | 不重试，按错误诊断 |
| 无法解析，也不是工具错误的形态 | `malformed_response` | 不重试，记录原文并检查工具语义 |

要点：

- 合法批次永远优先。即使批次带 `isError`，或子任务正文里恰好出现超时字样，也按任务结果处理。
- 只有整句匹配的标准超时诊断才续等，正文里出现一个 `timeout` 单词不算。
- 一次调用内部不能被打断。在途调用即使超过 30 分钟上限，也照常收取它的结果；上限只在下一次续等之前检查。
- 直接调用模式下，每次正常超时返回都会唤起一次主模型。这是宿主时限造成的固定成本，不要再额外插入查询。
- Claude Code 主宿主实测：单次等待在 1800 秒没有响应时被客户端中止，正好等于一个停滞窗口，因此每 30 分钟唤起一次主模型、做一次停滞检查。这个时限可以通过 MCP 服务的 `timeout` 配置或 `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` 调整，但修改需要用户授权；**不建议设为 0（禁用）**，否则卡死的子任务会让主代理永远阻塞在一次调用里，停滞检查永远不会发生。

## 4. 等待期间的沟通

- 纯等待期间不输出“还在跑”“继续等”这类消息，直接续等。
- 只有三种情况要说话：拿到终态结果、子任务 `blocked_on` 需要用户处理、需要用户做决定。

## 5. 停滞处理：进度感知，主代理自主

收到 `stalled` 后，每个停滞检查点只做这两次只读调用，然后与等待记录里的上一次快照比较：

1. 对全部待处理任务做**一次**不带 `wait_ms` 的 `get_delegation_status` 快照，读取每个任务的 `progress.steps` 和 `last_step`。这是检查点内唯一允许的非阻塞查询，不能连续调用。
2. 对快照里没有 `progress` 的任务，用 `child_conversation_id` 调用一次 `get_session_info(session_id, max_messages=1)`。

**进展信号**（任一变化即算有进展）：`progress.steps`、`stats.total_duration_ms`、`message_count`、`stats.context_window_used_tokens`。**不能只看 `updated_at`**：实测中，一个正常工作 25 分钟的子会话，`updated_at` 一直停在开始后的第 8 秒（见兼容性记录）。

**长命令例外**：如果最近一条消息说明正在执行一条有预计时长的命令，并且按开始时间推算还没到点，就不算停滞，直接续等。任务书模板要求子代理在长命令开始前写明预计时长，就是为了这一点。超过声明时长后仍然没有任何进展信号，按无进展计算。

| 情形 | 动作 |
| --- | --- |
| 有进展，或长命令尚未到点 | 更新快照，不发消息，开始下一段等待 |
| 第 1 次无进展 | 记录下来，开始下一段等待 |
| **连续 2 段无进展**（默认约 1 小时） | 判定为卡死：先用 `cancel_delegation` 取消，核对实际文件状态和成果，再带上现场信息重派**一次**。重派计入失败升级的尝试次数。取消后检查返回状态：如果仍显示 `running`（例如缓存已丢失，取消不起作用），确认没有残留进程和副作用后，不再重复取消，在最终汇报里说明这个“僵尸”会话 |
| 重派后的任务再次判定卡死 | 带证据（两次的快照、最后一条消息、已做的检查）问用户 |
| **后台命令挂起的快速判定**：子代理最后一条消息说它启动了后台命令并在等待，一个停滞窗口内没有任何进展信号，且只读检查确认该命令的进程已经不存在 | 不必等第二个窗口，直接按卡死处理（实测 Antigravity 多次出现这种挂起） |
| 没有 `child_conversation_id`，无法判断进展 | 不取消。累计 4 段（约 2 小时）仍无结果时，带证据问用户 |

这是本技能默认授予主代理的处置权限。用户明确要求“不要取消子任务”或“卡住先问我”时，以用户指令为准。只是不想再等时，停止等待即可，不要取消子任务。

## 6. 断联、中断与缓存丢失

| 现象 | 含义 | 动作 |
| --- | --- | --- |
| 等待调用报 “Tool call interrupted”、会话中断，或上下文恢复后不知道上次等待的结果 | 主会话侧的调用断了，子任务可能还在运行 | 先不带 `wait_ms` 查一次状态，核对等待记录。任务还在就用**原任务 ID** 续等，**不重派** |
| `wait_ms=0` 立刻返回纯 `running`，消息里有 `Result no longer cached` 之类的说明 | broker 已经丢失这个任务的等待能力，再调用也会立刻返回 | 改以子会话为准：用 `get_session_info` 查子会话。已结束，就从子会话读取结果；仍在运行，就设**一次**定时唤醒（见下） |

**单次定时唤醒**：等待工具无法阻塞时，用宿主提供的一次性定时机制（例如后台计时命令、定时唤醒工具），在有证据的时间点唤醒一次，再查一次子会话。时间点优先取子代理声明的预计结束时间，没有声明就取一个停滞窗口（30 分钟）。每次唤醒后按第 5 节判断进展。禁止用短间隔定时器反复查询。宿主没有任何定时机制时，交接给用户：说明任务 ID、子会话引用、最后状态，以及重新收取结果的方法。

## 7. 执行单元模式的额外规则

- 外层返回 `Script running with cell ID ...` 时，只代表外层让出了控制权，内层等待可能还在进行。记录这个单元 ID，用宿主的恢复接口（例如 `functions.wait`）继续等**同一个**单元。
- 同一组任务已有未完成的等待单元时，不再创建第二个等待。先收取原单元的结果。
- 外层恢复采用宿主允许的最长时段，不为了频繁查看而用 1 秒、10 秒这样的短等待。
- 外层恢复仍可能唤起模型、消耗上下文。不要声称“零 token”或“完全后台回调”。

## 8. 多任务与多会话

- 同一主代理的多个子任务放进同一个 `task_ids` 批次一起等。任一任务可操作就返回，处理后移出终态任务，剩余任务继续等。
- 已结束的任务不要再放回集合，否则会导致等待立即返回。
- 不同主会话各自持有自己的任务和等待，没有全局锁。禁止的是同一任务的重叠等待。
- 正在进行的等待使用固定的 ID 集合。新派发的任务记录下来，在下一次等待时合并进来。
