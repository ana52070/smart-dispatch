# 各宿主实测记录

本文件是仓库里**唯一**记录实测数据的地方，其他文档只引用这里。每条记录都只代表一次本地验证，不是永久保证。原始日志、会话记录、任务标识、机器指纹和安装路径不随仓库分发，这里只保留可以复核的结论、量级和边界。

## 总览

| 主代理宿主 | 等待模式 | 单次调用的客户端时限 | 标准超时报错 | 状态 |
| --- | --- | --- | --- | --- |
| Codex（`functions.exec` / `functions.wait`） | 执行单元模式 | 约 300 秒 | `timed out awaiting tools/call after 300s` | 已实测（控制器 1.0.0） |
| Claude Code（Claude Agent SDK 宿主） | 直接调用模式 | 1800 秒空闲中止 | `MCP server "codeg-mcp" tool "get_delegation_status" sent no response or progress for 1800s; aborting. …` | 已实测（技能 1.1.0） |
| Antigravity、CodeBuddy 等其他主宿主 | 直接调用模式（默认） | 未测 | 未测 | 未验证：按判定表处理，遇到不认识的超时格式时按 `transport_error` 交接 |

其他代理作为**执行子代理**时，不需要具备执行单元。

## Claude Code 主宿主（2026-11-16，技能 1.1.0）

环境：Codeg 中的 Claude Code 主会话（Claude Agent SDK 0.3.323），执行子代理为一个 Antigravity 自定义代理，在 Windows 本机运行。

### 长等待

- 子代理被要求在前台累计睡眠 1500 秒。它的命令工具单条上限为 600 秒，第一次 1500 秒的命令失败后，改为 5 条 280 秒加 1 条 110 秒，合计真实睡眠 1510.031 秒，子任务总耗时 2334.9 秒。
- 主代理直接调用 `get_delegation_status(wait_ms=0)`：第 1 次调用在 **1800.69 秒**被客户端中止，返回上表中的空闲超时报错；按判定表用同一 ID 续等，第 2 次调用 497 秒后收到 `completed` 和预期标记。
- 整个过程只有 2 次等待调用、1 次停滞检查点，没有 `wait_ms>0` 查询，也没有重派。
- 报错提示这个时限可以通过 MCP 服务的 `timeout` 配置或 `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` 调整。本次没有修改任何配置。

### 进度信号

- 一个正常工作的子会话，`updated_at` 在开始后 8 秒就不再变化，持续 25 分钟以上；`message_count` 同样不变。
- 同一时段 `stats.total_duration_ms` 持续增长，不带 `wait_ms` 的状态快照里也有 `progress.steps`、`marks` 和 `last_step`。
- 结论：判断进展不能只看 `updated_at`，必须同时看 `progress.steps` 和 `total_duration_ms`。

### 断联、缓存丢失与卡死

- 另一个子任务等待到约 11 分钟时，主会话断联，等待调用返回 “Tool call interrupted”。
- 恢复后，用原任务 ID 做状态快照，结果仍是 `running`。此后 `wait_ms=0` 会**立刻**返回纯 `running`，附带 `Result no longer cached; open child session … for the full output.`：broker 已经丢失这个任务的等待能力。
- 这个子会话在声明的结束时间过去 25 分钟后，`updated_at`、`message_count` 和 `total_duration_ms` 都没有任何变化，子代理启动的睡眠进程也已经退出。按停滞规则判定为卡死。
- 对它调用 `cancel_delegation`，返回的仍是 `running` 和 “no longer cached”，会话记录也保持 `in_progress`：**缓存丢失后，取消不起作用**。系统里没有残留进程。

### 子代理的行为

- 任务书明确要求“前台执行、禁止后台”，Antigravity 仍然把每条命令作为它内部的后台任务（`task-N`）启动，再等待它完成。主代理无法通过任务书改变这一点，所以验收时要检查“后台进程已经结算”。

## 评测期间的补充观察（2026-11-16 至 11-17）

- **只允许一层委托**：由 `delegate_to_agent` 启动的会话里能看到委托工具，但实际调用会因深度限制失败。被委托的会话不能再委托，评测中的协作组因此改用分阶段接力。
- **Antigravity 后台命令挂起**：又出现 3 次。子代理说“已在后台运行 npm test，等待完成”，之后再没有任何进展；其中两次代码已经写完。重派同一份任务书后正常完成。
- **重启后缓存丢失**：Codeg 重启后，未收取的任务返回 `Result no longer cached`，状态可能显示为 `canceled`。工作目录里的成果还在，要以子会话和文件实际状态为准。
- `get_session_info` 返回的消息文本会被截断；需要完整结果时，应以 `get_delegation_status` 的结果为准。

## Codex 主宿主（2026-11，控制器 1.0.0）

环境：Codex CLI 0.165（`functions.exec` / Code Mode）、Codeg 桌面应用 0.42.1（生产安装）、随 Codeg 安装的 `codeg-mcp`。本地源码后端测试来自另一份开发基线（0.41.3），不能等同于生产 0.42.1 进程内的状态。

### 长等待

- 单个 CodeBuddy 执行子代理真实睡眠 650.0 秒；控制器在同一执行单元中累计等待 1043.053 秒（差值来自子代理启动阶段修正自身命令引号）。
- 四次串行等待调用：前三次各在约 300 秒返回客户端超时，控制器自动续等（每次都是 `wait_ms:0`）；第四次收到 `completed` 和预期标记。
- 开始阶段的真实工具权限阻塞被及时返回为可操作结果。平台强制的授权仍然需要用户处理。

### 超时与连接释放（隔离管道）

使用已安装的伴生程序、私有测试命名管道、自建测试令牌和本地模拟模型，没有读取用户令牌。

1. 显式发送 `notifications/cancelled` 后，查询管道约 0.119 毫秒关闭，早于测试进程退出。
2. 工具超时设为 1 秒并连续查询两次：观察到两个 `after 1000ms` 错误和两个 ID 匹配的取消通知；两个管道都在取消通知后约 0.272 毫秒关闭；同时存在的查询连接最多 1 个，结束后为 0。
3. 本地源码后端的“对端关闭时结束等待、不取消子任务”测试通过。

长等待和隔离释放是两套独立的证据，不能合并成对生产 broker 内部计数的直接采样。

### 1.1.0 的变化对 Codex 的影响

控制器 1.1.0 默认每段最多等 30 分钟。按 300 秒的客户端时限计算，一段最多 6 次调用，之后返回 `stalled`，由主代理做停滞检查。这部分逻辑由单元测试覆盖，还没有在 Codex 上重新做真实长测。

## 尚未验证的范围

- 生产 Codeg 内部的存活等待数、连接持有时间和堆内存都没有直接采样。
- 超时边界附近的提问去重、多个真实主会话高并发、应用退出或强制终止后的清理路径，都没有做完整的压力验证。
- 缓存丢失后，如果子任务后来正常完成，结果能否从子会话完整读取，本次没有观察到（卡死的那个子任务一直没有完成）。
